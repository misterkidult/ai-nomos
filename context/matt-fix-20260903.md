## 1. 改了什麼

### 1-1　S4／M3：url scheme allowlist（`api/findings.js:27-40`）

新增兩個模組層 helper，放在 `sha16` 旁邊：

- `api/findings.js:33-38` `isHttpUrl(u)` —— 非字串或空字串直接 false；其餘丟進 `new URL()`，只有 `protocol === 'http:'` 或 `'https:'` 回 true，**解析丟例外就回 false**。沒有任何字串比對：附錄二實測的四種變形（`javascript:`／`JaVaScRiPt:`／前置空白／內嵌 tab）全部由 `new URL()` 正規化後在 `protocol` 這一關被判掉。
- `api/findings.js:40` `badSource(f)` —— 只在「`source.url` 存在且 truthy，但不是 http(s)」時為 true。`source` 缺席或 `url` 是空字串仍算貼上文件（契約 §1 允許），行為不變。

擋在哪一層、為什麼：**擋在 `api/findings.js` 的入口，不進 `api/_locks.js`**（`api/findings.js:146`，與 §3 鎖判定同一個 forEach，但是獨立的 or 條件）。三個理由：

1. **`_locks.js` 修不掉 S4。** M3 的判定 `isPublicArticle`（`api/_locks.js:54`）只決定「要不要跑 PII 正則」。就算在那裡加上 scheme 驗證，一筆帶 `javascript:` url 的 finding 只會被改判成「貼上文件」，PII 沒命中就照樣**存進去、照樣進 `href`** —— S4 完全沒修到。
2. **這不是 §3 的鎖。** §3 的九條鎖是逐筆自洽性檢查，`scripts/check-findings.py` 這支無依賴的參考實作算得出每一條。「url 的 scheme 合不合法」需要一個 URL 解析器，py 那側要跟上就得自己寫一份 WHATWG URL 正規化 —— 那才是真正會讓兩邊分岔的東西。放在入口層，py／js 的判定面完全沒被碰到（驗證見 §2）。
3. **M3 一起修掉，而且修得更徹底。** M3 的攻擊是「加一個 `source:{url:"x"}` 讓 PII 鎖跳過」。`"x"` 過不了 `new URL()` → **整筆被擋**，比「讓 PII 鎖重新生效」更嚴：夾帶個資的內容連被判定的機會都沒有。合法 http(s) url 仍照契約 §3 豁免 PII —— 那是規格要的行為，沒有改。

### 1-2　S1：覆寫需同 submitter（`api/findings.js:174-210`）

原本 `HMGET docterm` 命中就直接把舊 id 拿去 `SET`（舊 `api/findings.js:151,162`），而覆寫鑰匙的兩半（`sha16(source.url)`、`term_key`）**都是 ★ 公開欄位**，所以「命中」不構成任何所有權證明。

新增的流程：

- `api/findings.js:188-199`　拿 `HMGET` 回來的 id 去讀原紀錄（`GET sighting:<id>`，去重後一批送出），把 `id → submitter` 記進 `owner` Map。三種取值：
  - row 讀得到且 `submitter` 是字串 → 記那個字串
  - row 讀得到但 `submitter` 不是字串（**開張那 1,314 筆就是這種，`scripts/kv-load.py:60-67` 的 row 沒有這個欄位**）或 JSON 解析失敗 → 記 `null`
  - `GET` 回 null（docterm 指向一筆不存在的 row）→ **不進 Map**
- `api/findings.js:201-209`　逐筆判定：`id && owner.has(id) && owner.get(id) !== submitter` → 擋下，計入 `rejected`；否則進 `writable`。
  - 因為 `submitter` 一定是非空字串（`api/findings.js:112` 預設 `'anonymous'`），`null !== submitter` 恆真 → **開張那 1,314 筆從此永久不可透過本端點覆寫**，這是拍板要的行為。
  - `owner.has(id)` 為 false（row 不存在）→ 放行。docterm 指著一筆不存在的紀錄時沒有東西需要保護，寫進去是「建立」不是「覆寫」；這條也正是 `scripts/kv-backfill-docterm.py` 的 legacy id 重用路徑（既有測試第 6 節盯著這件事）。
- `api/findings.js:213-243`　後續全部改吃 `writable`（原本吃 `accepted`）：`byDoc`／`langOf`／`rows`／`HSET docterm` 的 pair 都跟著換。`pair` 與命中的 `id` 隨 finding 一起帶在 `writable` 的元素上，不再靠 index 對齊兩個平行陣列。

`accepted` 的元素型別跟著變了：從裸 finding 變成 `{f, index}`（`api/findings.js:147`）—— 因為被擋下的那筆要回報原始 index，而 `accepted` 已經是過濾後的陣列。

### 1-3　回報機制（`api/findings.js:130-141`）

依決定二**沒有新增任何拒絕碼**。兩個守衛擋下的 finding 都：

- 計入 `rejected`，帶 `{index, term_raw, reasons: []}`
- `accepted + rejected.length` 仍等於送進來的筆數（帳對得起來）
- 契約 §5 的回應形狀不變（`reasons` 是陣列，空陣列合法）

順手把三處重複的回應組裝收成一個 `answer(n)`（`api/findings.js:139-141`、`150`、`210`、`256`）—— 因為 S1 的過濾多出一個「全部被擋」的早退點，不收會變成三份一樣的 JSON 字面值。

前端不用改也不會壞：`public/index.html:313` 是 `(x.reasons || []).map(...)`，空陣列渲染成 `詞（）`。**醜，但不是壞掉** —— 這件事寫進 §5 未決事項。

## 4. 這個修法擋不住什麼

按殘餘風險排序，都不是這輪的漏做，是這個修法在設計上就到不了的地方：

1. **`submitter` 完全可偽造。** 它是 body 裡的字串（`api/findings.js:112`），沒有任何驗證。攻擊者只要**從公開回應讀出目標紀錄的 submitter，就能冒充它去覆寫** —— 但 `submitter` 是 §4 標記不公開的欄位，`api/sightings.js:17` 也真的丟掉了它。所以攻擊者拿不到別人的 submitter 值，只能猜。**S1 從「照抄公開欄位就能改」變成「要猜對一個看不到的 64 字元字串」** —— 這是這次修補真正買到的東西，但它是「未公開」而不是「認證」，跟 M1 是同一種脆弱：哪天有人把 `submitter` 加進 `PUBLIC` 陣列，S1 立刻整條復活。**這正是附錄二對 `target="_blank"` 的擔憂的同型 —— 防線寄生在別的決定上。** 建議把 `api/sightings.js:12` 的 allowlist 註解補一句「submitter 現在是 S1 的唯一防線」，或另派一輪做真的簽章。
2. **預設 `submitter` 是 `'anonymous'`。** 沒帶 `submitter` 的呼叫者共用同一個身分，**彼此的紀錄可以互相覆寫**。這批紀錄是誰餵的分不出來，本來也分不出來。要收緊就得拒絕沒帶 submitter 的請求 —— 那會改變契約 §4「a limit, not a security feature」的語意，不在這輪範圍。
3. **自己改自己的沒有擋。** 同一個 submitter 可以無限次改寫自己餵過的每一筆，改成任何過得了九條鎖的內容，沒有版本、沒有稽核欄位、改完 `ZADD recent` 還會把它推到動態牆最上面（`api/findings.js:242`）。這是契約 §5 明文要的行為，不是漏洞；但「不可還原」這件事沒有變 —— 要修得靠 append + 標記取代（報告 S1 的方向三），那是改契約的事。
4. **新增紀錄一點都沒擋。** 攻擊者換新的 url 就是全新的 (文件, 詞)，永遠 writable。這輪修的是「污染既有資料」，不是「灌新資料」—— 後者要靠 S2（欄位上限）與 M1（限速），兩條都明列不在這輪。
5. **合法 http(s) url 不代表那是真的文章。** `https://attacker.example/` 過得了 `new URL()`，所以：
   - 動態牆上仍可掛任意惡意連結，外觀與正常來源無異（附錄二說「這條確定的危害不變」，**這輪沒有修掉它**，只修掉了 `javascript:`／`data:` 那半）
   - M3 的 PII 豁免仍可被一個語法合法的假 url 繞過。要真的修，得驗「這個 url 真的存在且引句真的在裡面」—— 那需要伺服器去 fetch 那篇文章，而報告「已經做對的」第 4 條講明產品刻意不做（零 SSRF 面）。**這是架構層的取捨，不建議為了 M3 動它。**
6. **docterm 沒 backfill 到的 legacy 紀錄仍可被繞過。** 若某筆開張紀錄沒進 `docterm`，攻擊者送同一組 (url, term) 會在**推導 id** 上建一筆新的，legacy 那筆原封不動地留著 → 同一詞同一文出現兩筆並存（違反契約 §2 rule 6 的觀感問題，不是覆寫）。我沒有辦法從 repo 確認 `kv-backfill-docterm.py` 實際跑完了幾筆 —— 這件事在原報告「看不到什麼」第 5 條就列著，**上線前值得去 Upstash 對一次 `HLEN docterm` 與 `SCARD`／紀錄總數**。
7. **成本沒有變好，還變差一點。** 每個寫入請求現在多一趟 round trip 與最多 50 個 `GET`（`api/findings.js:191`）—— HMGET 的結果才知道要讀哪些 id，塞不進同一個 pipeline。寫入路徑有限速綁著（S1 攻擊那 74 個請求的估算不變，只是每個請求貴一點），但**這確實是在 S3 沒修的情況下多開的一點放大**。可接受，但要知道。
8. **併發覆寫是 last-write-wins。** 兩個同 submitter 的請求同時打同一筆，沒有 CAS、沒有版本比較，後到的贏。原本就是這樣，沒變差。
9. **`api/findings.js:146` 的 or 條件會吃掉一個鎖碼。** 一筆同時「url 不合法」又「夾帶 PII」的 finding，`checkServer` 因為看到 truthy url 而跳過 PII 正則，所以 `reasons` 是空陣列而不是 `['PII_DETECTED']`。兩種情況都是擋下，只是回報少一個碼。我刻意沒有為了補這個碼去餵 `checkServer` 一份「洗掉 url 的複本」—— 那會讓它回報一筆呼叫端沒送過的 finding，比少一個碼更難解釋。

## 5. 未決事項

1. **空 `reasons` 讓 agent 看不懂發生什麼事 —— 這條我按交辦停手，交回去判。**
   決定二說「若評估後認為不新增碼就無法讓 agent 理解，寫進未決事項」。我的評估是：**兩個守衛裡有一個真的需要碼，另一個不需要。**
   - **覆寫被擋**：agent 拿到碼也沒有下一步（那筆不是它的，重試永遠失敗）。空 `reasons` 的資訊損失可接受。
   - **url 不合法**：這件事**是可行動的** —— agent 送個正常的 http(s) url 就過了。現在它只知道「有一筆被擋、沒說為什麼」，很可能原地重試同一個 payload。這是真的資訊損失。
   兩個建議，請挑一個：
   - (a) 這輪就這樣，下一輪走 `contract:` 流程一次補兩個碼（三處同步：契約 §3、`check-findings.py`、`_locks.js`）。**我推薦這個** —— 因為 url 那個碼要寫進 §3 才誠實，而 §3 一動就該連 `contract_version` 一起想。
   - (b) 只補 url 那一個碼（例如 `SOURCE_URL_INVALID`），覆寫維持空陣列。成本一樣是三處同步 ＋ `contract:` commit，省不了流程。
