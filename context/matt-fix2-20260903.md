## 1. 改了什麼

### 1-1　S2：大小與型別（`api/findings.js:44-93`、`:181-182`、`:221`、`:280`）

**新增的判定**

| 位置 | 內容 |
|---|---|
| `api/findings.js:44` | `cp(s)` —— 按 code point 數，與 `api/_locks.js:21`、`scripts/check-findings.py` 的 `len()` 同一種算法。emoji 在 JS `.length` 是 2、code point 是 1，兩邊要一致 |
| `api/findings.js:57-63` | `LIMITS`：`term_raw` 120／`term_normalized` 120／`sentence` 120／`context` 2000／`definition_quote` **300** |
| `api/findings.js:71` | `SOURCE_LIMITS`：`source.url` 2048／`source.title` 300／`source.published` 40 |
| `api/findings.js:72-90` | `badShape(f)` —— 上面每一欄「存在但不是字串」或「超過上限」即 true。`undefined` 一律放行（那是 §3 的 `MISSING_FIELD` 在管，不是我的事）；`source` 若存在必須是非陣列的物件 |
| `api/findings.js:221` | 掛進既有的那個 or 條件：`if (reasons.length \|\| badSource(g) \|\| badShape(g))` |

**不截斷**：`badShape` 只回 true／false，沒有任何地方寫回 `f`。超過上限＝整筆進 `rejected`，儲存裡不會出現它的任何前綴（測試 `S2：超長引句沒有被截斷後存進去` 直接掃整個 store 驗這件事）。

**`context` 為什麼是 2000**（委託方要我自己定並說明理由）：

1. **它不落地**。`api/findings.js:245-262` 組 row 時根本沒有 `context` 這個欄位（既有測試 `stored: sentence/context NEVER stored` 盯著），所以它不會變成儲存成本，也不會出現在任何一次 `GET /api/sightings` 的回應裡。這是可以放寬的理由。
2. **但仍必須有界**。它是攻擊者提供的，且 `definition_quote` 只要是它的子字串就過 §3（`api/_locks.js:33`）—— 只限 300 而放任 `context`，body 仍可塞到 Vercel 的 4.5 MB 上限，佔用的是解析成本與函式執行時間。
3. **2000 這個數字怎麼來的**：契約 §1 定義 `context` ＝「`sentence` 加前後各一句」，而 `sentence` 有明文 `≤ 120`。三句同級距約 360 字。2000 給了前後句 5 倍以上的餘裕（英文長句、含引號的段落都放得下），同時把一次 50 筆的請求從 4.5 MB 壓到約 10 萬 code point（UTF-8 下約 300 KB）。**它遠大於 300，所以「引句必須是 context 的子字串」在滿長度時仍成立** —— 不會出現「引句合法但塞不進 context」的死角。

**型別**：報告 S2 指出的原攻擊是 `term_raw` 傳巢狀物件 —— 鎖看的是 `String(f.term_raw)` ＝ `"[object Object]"`，只要 `sentence` 含這一串就過九條鎖，但 `api/findings.js:258` 存的是**原始物件**。新測試 10c 第一筆就是照這個攻擊逐字重建的，過得了 §3、只被 `badShape` 擋下。

**我自己多加、拍板沒有指名的三件事**（請看第 5 節，我把它們列為未決）：

- `term_raw` / `term_normalized` 上限 120。**理由**：只做 `definition_quote` 300 的話，S2 沒有被修好，只是換了個欄位 —— `term_raw` 同樣是 ★ 公開欄位、同樣原樣落地，而它的「隱性上限」只在 `sentence` 非空時才存在（`api/_locks.js:29` 的 `if (t && s && …)`）。送 `sentence: ""` 就繞開了，`term_raw` 可以是 4 MB 並且存進去、並且出現在每一次公開回應裡。120 不是新數字，就是 §3 已有的 sentence 上限 —— 一個詞本來就得放得進自己的句子裡。
- `source.title` 300 / `source.published` 40 / `source.url` 2048。**理由**：這三個同樣原樣落地（`api/findings.js:263`）並且公開（`api/sightings.js:19`）。`url` 的 2048 是瀏覽器與 CDN 的傳統界線。
- `rejected[].term_raw` 與 `not_found` 的回吐上限（`api/findings.js:93`、`:181-182`）。**理由**：這兩個是把呼叫端送來的字串**原樣回吐**。不設界的話「拒絕」本身就是放大器 —— 50 筆各 4 MB 的 `term_raw` 送進來、全部被拒、再原樣吐 200 MB 回去，攻擊者一毛錢沒花。`term_raw` 的回吐是**標籤不是資料**（給呼叫端對出是哪一筆），所以這裡用截斷（120 code point）而不是拒絕；`not_found` 超過 120 的直接濾掉，與該行原本就在濾非字串與空白是同一種處理。

### 1-2　S3：讀取端點硬上限 200（`api/sightings.js:46-61`）

```
:54   ZREVRANGE by_term:<k> 0 199          （原本 0 -1）
:57   ZREVRANGEBYSCORE recent +inf <since> LIMIT 0 200   （原本無 LIMIT）
:59   ZREVRANGE recent 0 199              （不變）
```

**兩層都做**：`LIMIT` 讓 range scan 在 Redis 端就停，`slice` 是不管指令回什麼都成立的天花板。報告 S3 真正的放大在 `api/sightings.js:66` —— 每個 id 都變成一條 `GET`；封頂 ids 就等於把「一個 HTTP 請求 → 約 1,300 個 Redis 指令」壓成「→ 最多 202 個」。新測試直接數送出去的 `GET` 指令筆數來驗這件事，不是只看回應長度。

### 1-3　M1：XFF 陷阱（`api/findings.js:95-113`、`:196`）

新增 `clientIp(headers)`，`api/findings.js:196` 從

```js
const ip = (req.headers['x-forwarded-for'] || '').split(',')[0].trim() || 'unknown';
```

改成 `const ip = clientIp(req.headers);`。

**選的是「取 `x-forwarded-for` 的最後一段」，不是 `x-real-ip`。理由是委託方要求的那一條：不管 Vercel 行為如何都安全。**

- XFF 的語意是一個由近而遠追加的清單，**只有「最靠近的可信代理剛剛附上的那一段」值得相信**；呼叫端送來的東西在語意上只能排在它**前面**。
- 若 Vercel 是**覆寫**：整個 header 都是 Vercel 寫的，最後一段就是它認定的 client。安全。
- 若 Vercel 是**附加**：呼叫端的偽造值排在前面，Vercel 剛附上的真實 client ip 是最後一段。安全。
- **兩種行為下答案都對，所以這個寫法不需要我去打線上端點驗 Vercel 到底是哪一種** —— 這正是交辦要的性質。取第一段（舊碼）在「附加」情境下拿到的**字面上就是攻擊者自己送的字串**，這是 XFF 的經典陷阱。
- **為什麼不用 `x-real-ip`**：它單獨用**不**具備這個性質。若 Vercel 沒有覆寫掉呼叫端送來的 `x-real-ip`，那整個值就由攻擊者控制，比現況更糟；而要確認 Vercel 有覆寫，就得去打線上端點 —— 正是這輪不做的事。

附帶兩件小事（`api/findings.js:105-113`）：

- 取到的值先剝 `[::1]` 這種括號形式、剝 IPv4 的 `:port`，再驗它像不像 IP 字面值。
- 驗不過（或整個 header 不存在）→ 落到單一的 `'unknown'` 桶。這是**更嚴、不會更鬆**：所有無法識別的呼叫者共用一個每小時 120 的額度。

## 3. 契約待補的差異（**這節需要委託方決定**）

### 3-5　不補的話會怎樣

**這是拍板要我具體寫出來的部分：**

1. **一個守規矩的 agent 會被拒絕，然後在契約裡找不到任何依據。** 它從 `feedDocument` 拿到的 `finding_schema`（`:60`）說 `definition_quote` 是無上限的 `string`，它照做送了一段 400 字的定義段落 —— 那是**完全合乎規格的行為** —— 卻拿回一筆 `rejected`。
2. **而且拿回的是空的 `reasons`。** 依拍板「不新增 enum」，這輪的守衛跟上一輪一樣回 `reasons: []`。所以 agent 收到的訊息是「有一筆被拒、沒說為什麼」，它去查契約 §3 的九個碼，一個都對不上；查 §1 的欄位定義，寫著沒有上限。**它唯一合理的下一步就是原地重試同一個 payload** —— 而重試永遠會失敗。這是一個無聲的無限迴圈，而且每次重試都真的消耗 `PER_SUBMITTER_HOURLY` 與 Upstash 指令。
3. **人也會踩到同一顆雷。** 契約是「頁面、`api/*`、餵食三方的唯一依據」（CLAUDE.md）。下一個接手 `api/findings.js` 的人讀契約，會認為 `LIMITS` 那張表是憑空冒出來的魔術數字，很可能在重構時把它拿掉。
4. **參賽場合的具體風險**：評審若照契約寫一個 agent 來餵，長引句的文章會靜默失敗，而 demo 現場沒有任何訊息解釋為什麼。

**最小的補法**：光補 §3-1 的兩行就解掉第 1、3、4 點。第 2 點（空 `reasons`）補契約解不掉 —— 那要新增拒絕碼，見第 5 節未決事項 2。

## 4. 這個修法擋不住什麼

按嚴重度排，前兩點是**這輪修補自己帶進來的**，不是既有殘餘。

1. **⚠ 首頁的 `?days=365` 現在只拿得到 200 筆。**
   `public/index.html:317` 與 `:555` 都是 `N.loadSightings('?days=365')`，而首頁的一切都從這份資料算出來：`draw()` 的 `groupByTerm`（`public/index.html:110`）、7／14／30 天的窗口統計（`:110`）、動態牆、`?probe` 的匯出（`:517-519`）。線上約 1,300 筆，加上這個上限後首頁只看得到最新的 200 筆 —— **「N 個詞 / N 篇文章」這些數字會明顯縮水，動態牆會少掉大部分歷史**。
   `contributors` 不受影響（走 `SCARD`，`api/sightings.js:60`）；詞條頁 `?term_key=`（`public/term.html:192`）實務上不受影響（一個詞頂多幾十筆）。
   這是拍板明文要求的（「`?days=99999` 與 `?term_key=x` 都要吃到這個上限」），所以我照做了，**但它是一個看得見的產品退化，不是純資安改動**。我不能動 `public/`，也不該自己決定要不要放寬。三條路，請委託方挑：(a) 接受首頁只顯示最新 200 筆；(b) 首頁改用 `?days=365` 之外的取數方式（例如把統計數字改成端點回傳的彙總欄位，而不是前端自己數）；(c) 上限放寬成一個大於現有語料量的數字（但那就等於沒有上限，S3 的放大回來）。**我推薦 (b)** —— 它同時解掉「首頁要下載整份語料」這件事本身。
2. **`?lang=` 是在封頂之後才過濾的**（`api/sightings.js:71-72`）。所以 `?days=365&lang=en` 拿到的是「最新 200 筆裡的英文那些」，不是「最新 200 筆英文」。以英文佔比不高的語料來說，回傳筆數會比預期少很多。要修得把 lang 推進索引（例如 `by_lang:` 或 `recent:en` 這種 zset），那是資料結構的改動，不在這輪。
3. **限速本身仍然不省錢。** `api/findings.js:199-201` 的 `INCR` 發生在任何驗證之前 —— 被 429 擋下的請求一樣花 2 個 Upstash 指令與 1 次 Vercel 函式呼叫。原報告附錄最後一列講的就是這件事，這輪沒有改變它。要真的省，得在到 Redis 之前擋（邊緣層或 WAF）。
4. **`clientIp` 在「Vercel 原樣穿透呼叫端的 XFF」這個情境下仍然會被騙。** 沒有任何 CDN 是這樣做的（那等於沒有任何 header 認得出 client），但這是這個寫法在邏輯上唯一的漏洞，誠實列出來。真的要確定，還是那一個 curl。
5. **`'unknown'` 桶是共用的。** 沒有可辨識 XFF 的呼叫者共用一個每小時 120 的額度。這是刻意選的「更嚴」方向，但代價是：若線上真的有一批合法流量落不到 IP，它們會互相排擠。本機測試（`headers: {}`）就是走這個桶。
6. **`submitter` 仍完全可偽造，且預設是 `'anonymous'`。** 上一輪已列，這輪沒變：S1 的防線是「攻擊者看不到別人的 submitter」而不是認證，而 `?days` 封頂**讓這件事稍微好一點點**（一次能撈到的目標少了），但一點也沒改變本質。
7. **新增紀錄仍然沒擋。** 攻擊者換新的 url 就是全新的（文件, 詞），永遠寫得進去。這輪的 S2 讓每一筆的體積有界（一筆最多約 300＋120＋300 字落地），但**筆數**只受 `PER_IP_HOURLY=120 × 50 筆`＝每小時 6,000 筆的限制 —— 一天就能把 `recent` 灌到十幾萬筆。封頂讀取讓它「打不掛站」，但灌進去的東西不會自己消失，`recent` 這個 zset 會無限成長。**S2＋S3 修的是單次的傷害，沒有修「慢性成長」。**
8. **合法 http(s) url 不代表那是真的文章。** 上一輪已列，這輪沒動：動態牆上仍可掛任意惡意連結，外觀與正常來源無異。
9. **`badShape` 不會告訴呼叫端是哪一欄超標。** 依拍板不新增拒絕碼，所以「引句 301 字」與「`term_raw` 是物件」在回應裡長得一模一樣（`reasons: []`）。見第 3-5 節第 2 點。
10. **M2（CORS `*`）與 M4（安全標頭）依交辦這輪不做。** M2 讓限速可以分散到真實訪客的 IP 上 —— 它直接削弱這輪修好的 M1：`clientIp` 現在算得對了，但攻擊者可以改用別人的瀏覽器來打。**M1 修好之後，M2 就是限速這條線上剩下的那個洞。**
