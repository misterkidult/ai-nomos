### 1-2 `site/` 要不要有後端

- **不要動 `site/index.html`**。它是 281 行單檔靜態站，`fetch('terms.json')`（index.html:268）之外沒有任何外部依賴，這是它現在唯一的優點。
- 正解是**加兄弟頁**：同一個 Vercel 專案下新增 `site/read.html`、`site/review.html` 與 `api/*`，字典本體維持零後端。
- `CLAUDE.md` 部署段寫「沒有 build step 要跑在 Vercel 端」——加了 `api/` 這句話就不再成立，`vercel build --prod` 會編譯 function。這是文件要同步改的地方，不是阻礙。

### 1-3 registerTool 怎麼接 `build.py`

- 方向要分清楚：`build.py` 是 `terms/*.md` → `site/terms.json` 的單向產生器（build.py:117-171）。目擊是反方向，**8 天內不要讓提交回寫 `terms/*.md`**，那需要格式化、lint、比喻段人眼檢查（`TERM-TEMPLATE.md:118`），不可能自動化。

- 三條鎖建議寫成 `verify_sightings.py`（沿用 uv PEP 723 慣例），端點呼叫同一份規則，避免 JS 與 Python 各寫一次然後分歧。

## 2. 資料契約與三條鎖

### 2-1 哪裡會被繞過

- 三條鎖（brief:40）全部是**對 agent 送來的文字做內部一致性檢查**。伺服器看不到原文（brief:18「文件不上傳」），所以一段完全捏造、但 `definition_quote ⊂ sentence` 且含 term 的紀錄，三條鎖全過。鎖驗的是格式良好，不是真實。
- `source.hash` 由客戶端算（brief:37），既是去重鍵、又是 🔥 的計數基礎（brief:44「不同文件數」）與定型第二態的門檻（brief:45「≥2 份文件」）。**改 hash 就能自己把一個詞推進「傳開中」**，單一使用者即可。這是整份契約最軟的一點。
- 「或緊鄰句」根本無法驗——緊鄰句沒有欄位。要能查就得多收一個 `context`（原句±1 句），鎖改成 `quote ⊂ context`。

### 2-2 哪裡會誤殺

- 「sentence 必含 term」與 brief:60「aka 正規化 agent 自己做得好」互相打架：agent 一旦把「檢索增強生成」正規化成 RAG，sentence 就不含 term，正常提交被擋。契約要拆成 `term_raw`（照原文，brief:52）＋ `term_normalized`，鎖只查 `term_raw`。
- 其他誤殺型態：詞出現在標題／表格欄位而定義在下一句；大小寫與空格差異（`Multi-Agent` vs `multi agent`）；跨句主詞省略的中文長句。
- enum 鎖無害，但 brief:60 說約四成是「邊緣＋順帶提到」會被 brief:40 的規則直接丟——實際良率約六成，Haiku 閘才是真正的過濾器，三條鎖有淪為裝飾的風險。

### 2-3 firm＝30 天無新 definition_quote 的漏洞

- **指標方向反了**：它量的是「有沒有人餵文件」，不是「定義有沒有穩」。冷門詞零流量會自動 firm——最沒被驗證的詞最快定型。
- 反面同樣壞：熱門詞每週都有含定義句的新文件，就算每次講的一模一樣也永遠 firm 不了。結果是「最穩的不 firm，最沒人看的秒 firm」。
- v1 無語意比對（brief:68），所以「新 definition_quote」＝任何字面不同的引句，同義改寫、同一份文件排版差異導致 hash 不同，都會重啟 30 天。
- 8 天內最便宜的修法是**改名不改演算法**：前端顯示「安靜 30 天」而不是「定型」，成本 0 且不騙人。要保留 firm 語意，最低限度得加「≥N 份不同文件」下限＋一次 Haiku「這兩句講的是同一件事嗎」。

## 4. 安全

- **綁頁面 session token 擋得住**：curl 直打端點的批次灌、隨手爬蟲、跨站來的雜訊。就這樣。
- **擋不住**：token 發給任何開得了 `/read` 的人。開一次頁，在 console 直接 fetch 迴圈就繞過 agent；重放同一個 token；多開分頁換 token。
- 三道防灌水（端點不公開、session token、匿名 submitter id，brief:15、38）**全部由客戶端掌握**——`submitter` 是瀏覽器自己產的 id，清一次就換人。要真限速只能綁 IP＋server 端配額。
- brief:15 把「不能批次餵」當防灌水是誤解：那限制的是使用門檻，不是寫入速率。
- **去識別化只靠 agent 的風險**：recall 沒有下限，漏一個客戶名就把第三方提案內容公開上站——而 `/review` 是公開列來源句的（brief:20、46）。`build.py:85-86` 的註解自己說明了為什麼不放通用商業詞，也就是說既有關卡設計上就抓不到未知公司名。
- 最低成本補法：伺服器端 regex 攔 email／電話／統編／金額／URL；Haiku 閘同時判「這句能不能認出特定公司或人」；`sentence` 設硬上限（約 120 字）；**預設只公開 `definition_quote`，不公開整句 sentence**——公開得越少越安全，順便讓 demo 畫面更乾淨。
- 小事但便宜：`source.hash` 若是原文直接 hash，等於可比對的指紋，有原文的人能驗證某份文件被提交過。加 salt。
